# Historical policy continuation

New requests and registrations always use the current approved, pinned bundle. Existing requests keep their original version and receipt; never overwrite those fields. A prior version is eligible for quote release/acceptance, order confirmation, manual reconciliation, staging, proof review and final release only when its immutable file matches an explicitly configured historical SHA-256 pin AND the customer's recorded digest. The current bundle must also remain valid and the relevant commercial flags enabled. Existing current-version legacy records without a receipt remain compatible; once they become historical, they require individual review rather than fabricated consent. Previously released artwork download authorization retains its existing payment and ownership checks; historic agreement changes are not used to revoke access automatically. Refund/hold controls remain available under their existing global gates. Historic policy URLs resolve only current or explicitly pinned archived documents. No policy or switch changed live. Synthetic integration tests now carry a historical request through quote acceptance, payment, review and delivery, including mismatch denial. Before any actual policy transition, obtain owner/legal approval for old-version continuation, retain all published documents, pin them, and verify all in-flight cases. This is not a mechanism for automatically applying new terms or obtaining fresh consent.

Receipt validation explicitly distinguishes pre-receipt legacy records (missing metadata) from malformed records and rejects mismatched receipt versions. The artist detail policy field is cleared by the same private-data cleanup routine as other request data. Synthetic tests include missing archive pins and corrupted current receipts.

## Operator transition checklist

1. Pause new intake while leaving existing customer history accessible. Inventory non-closed requests and paid orders before changing policy configuration.
2. Review and preserve the original published bytes in the repository. Confirm their hashes independently, and obtain explicit approval for grandfathering each applicable version. Never edit the old file in place.
3. Prepare the new approved bundle under a unique version. Confirm both the current and historical pins and check that every in-flight agreement has a matching receipt. Resolve missing or invalid records individually before switching.
4. Update the private current version, current digest, and archived pin map together. Verify the public policy reader and private workflow gates with an authorized test account; do not use real customer records as test fixtures.
5. Reopen intake only after the new version is verified. Retain archived documents and their pins for as long as necessary to support customer agreement access. Roll back the private configuration as a unit if eligibility unexpectedly fails.
